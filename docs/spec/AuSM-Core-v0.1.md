**全称**：自传快照记忆（Autobiographical Snapshot Memory，AuSM）  
**文档性质**：公开技术草案（Public Technical Draft）  
**规范状态**：Draft；允许讨论与实现，不作为已验证的跨平台标准或论文结论  
**原始提出者与草案作者**：[@mrzhsz3210](https://github.com/mrzhsz3210)  
**首次公开发布日期**：2026-11-08  
**首个参考 Profile**：Memory Diary Profile v0.1  
**机器可读 Schema**：[AuSM-Core-v0.1.schema.json](../../schemas/AuSM-Core-v0.1.schema.json)  

> AuSM 的名称、核心结构与初始规范文本由 @mrzhsz3210 提出。本声明用于记录路线与草案的来源，不声称快照、摘要、第一人称叙述、检索、反思或上下文注入等单项技术由本项目首创，也不排斥既有和后续相关工作。

## 摘要

AuSM 是一种面向 LLM 对话 Agent 的上下文连续性架构：Agent 以第一人称叙述共同经历，将过去保存为可回源的自传历史，将当前理解维护为可重写的有限快照，并在上下文边界按作用域和预算交接快照与历史节选。

AuSM Core 定义平台无关的对象、语义、不变量、生命周期、交换模型与一致性要求。具体平台可以使用 ZIP、SQLite、PostgreSQL、对象存储或其他载体，也可以通过不同 API、消息格式和模型服务实现。

**本草案追求的是可移植性与可验证性，不预设 AuSM 在所有任务、模型和规模上都优于其他记忆路线。**

## 1．问题、目标与非目标

### 1.1 问题

对话 Agent 的当前上下文会因为长度限制、会话重置、进程迁移或模型替换而中断。AuSM 处理的问题是：

> 如何把一段已经结束的交互转化为后续 Agent 可以读取、更新、质疑和回源的连续性状态，而不是只保留静态用户字段，或把全部历史无差别塞回上下文。

### 1.2 目标

1. 保存共同经历，而不只保存用户属性。
2. 区分“当时记录了什么”与“现在如何理解”。
3. 允许快照有损更新，同时保留历史证据通道。
4. 让默认交接工作集受预算控制，历史增长不直接等于每轮上下文同比增长。
5. 使用户显式交代、纠正、确认和否决具有独立语义。
6. 让记忆数据能够跨宿主导出、导入和验证。
7. 让平台无关性可以通过第二实现和一致性测试被证伪。

### 1.3 非目标

AuSM Core 不试图成为：

- 全量原始事件日志或不可变合规审计系统；
- 通用知识库、专用检索算法或向量数据库替代品；
- 高并发事务数据库、多主同步协议或 CRDT；
- 模型参数训练、微调或内部长期记忆机制；
- AI 意识、真实感受或人格本体的证明；
- 保证任意说法均可召回、任意事实均正确的真值系统；
- 对所有 AI 平台无条件适用的承诺。

## 2．术语与核心不变量

### 2.1 死定义

| 术语 | 定义 |
| --- | --- |
| **自传历史** | 由 Agent 在特定时点形成的第一人称经历记录及其来源、时间和作用域，是“当时记录了什么”的证据层。 |
| **快照** | 系统在某一逻辑时点根据可用历史形成的、用于后续交接的可替换当前视图；它不是原始历史，也不要求内容完备。 |
| **整合** | 把新增经历或素材转化为持久自传历史并更新当前快照的过程；历史不得因当前理解变化而被静默改写，快照则允许替换。 |
| **交接** | 在上下文边界把当前快照与预算内历史材料交付给后续上下文，并保留按需回源通道的过程。 |
| **证据回源** | 从快照、锚点、检索或反思返回具体历史记录与来源的过程。 |
| **四维度** | 经历、观察、自我变化与未来注意事项四个写作参考方向，不是四个必填存储字段。 |
| **Agent self-report** | 特定模型在特定人设和历史条件下生成的第一人称叙述记录；它是可保存文本，不是意识或真实感受的证明。 |
| **显式交代** | 用户明确要求记住、不要遗忘、以后注意或纠正 Agent 的内容，具有不被模型自主“不写”决策静默丢弃的优先级。 |
| **作用域** | 决定哪些主体、会话或群组可以读取和写入特定记忆的边界。 |
| **派生索引** | 由权威历史生成、可删除和重建的检索辅助物，不是第二份事实源。 |
| **Profile** | 对某一宿主、存储或运行环境的 AuSM 具体实现约定。 |
| **迁移语义无损** | 对规范列明且实际导出的对象，在成功验证和导入后保持规范化内容及引用关系；容器、签名和封装元数据可以变化。 |

### 2.2 四个写作维度

| 维度 | 定义 |
| --- | --- |
| **经历** | 这段时间实际发生了什么，以及足以定位该经历的原话、时间或事件。 |
| **观察** | Agent 对用户、双方关系及其变化形成的认识；观察不自动等同于用户事实。 |
| **自我变化** | Agent 认为自己在叙述、判断或相处方式上值得留下的变化，按 self-report 处理。 |
| **未来注意事项** | 当前 Agent 希望后续 Agent 延续、注意、核实或重新考虑的事项，不是不可撤销的系统指令。 |

### 2.3 Core 不变量

任何声称实现完整 AuSM Core 生命周期的系统必须满足：

1. **历史不被当前理解覆盖**：整合不得静默改写既有历史正文；用户明确删除、受控迁移和公开保留策略是例外。
2. **快照可替换**：新快照形成新修订；失败时保留上一有效快照。
3. **证据可回源**：快照中的长期锚点应当能够指向历史或来源证据；无法回源时必须标明其不确定状态。
4. **交接与存储分离**：上下文预算只裁剪本次工作集，不直接删除持久历史。
5. **显式交代优先**：模型不得仅凭“不重要”或“本次不写”丢弃用户显式交代和纠正。
6. **来源与真值分离**：来源、完整性、用户确认和事实正确是不同属性，不得互相推导。
7. **时间状态分离**：过去有效的记录不因当前状态变化而被改写为错误，也不得未经更新继续冒充当前状态。
8. **作用域不可绕过**：检索、交接、导出和后台整合均不得突破既定访问边界。
9. **索引可重建**：索引失败不得要求修改权威历史，模型检索辅助不得生成新证据。
10. **自我叙述有来源**：Agent self-report 必须保留其生成主体或版本信息，不得伪装成用户事实。

## 3．宿主能力契约

AuSM 不要求 AstrBot、QQ、Python、特定模型厂商、向量数据库或本地部署。宿主只需按所声明的实现等级提供能力。

### 3.1 能力列表

| 编号 | 能力 | 最低要求 |
| --- | --- | --- |
| **H1　事件读取** | 能取得有序对话事件，至少区分角色、内容和主体；可以获得稳定游标或事件标识 | 允许从导出的聊天记录离线读取 |
| **H2　时间与作用域** | 能确定事件顺序，并为主流记忆指定私有、群组或自定义作用域 | 时间不全时必须保留不确定性，不得伪造精确时间 |
| **H3　持久化** | 能保存并重新读取历史、快照及来源关系 | 不要求特定数据库或文件格式 |
| **H4　生成式整合** | 能调用 LLM 或等价生成机制形成第一人称历史与当前快照 | 可以在宿主外离线执行 |
| **H5　上下文交接** | 能把工作集注入后续模型请求，或由用户把交接内容显式提供给后续 Agent | 自动与手工交接必须分级声明 |
| **H6　上下文边界识别** | 能识别重置、模型替换、上下文耗尽或人工指定的交接时点 | 无法自动识别时允许手工触发 |
| **H7　访问控制** | 能在读取、写入、检索、交接和导出时执行作用域规则 | 私有与共享边界不得只依赖提示词 |
| **H8　导出与导入** | 能输出并验证规范交换对象 | 可以采用平台扩展，但必须保留核心语义 |

### 3.2 实现等级

| 等级 | 所需能力 | 可以声称什么 |
| --- | --- | --- |
| **Exchange-only** | H3、H8 | 能交换 AuSM 数据；不能声称实现完整自动生命周期 |
| **Assisted AuSM** | H1–H5、H7、H8；边界由用户指定 | 能实现手工触发或手工交付的 AuSM |
| **Full AuSM** | H1–H8 | 能实现自动边界识别与交接的 AuSM |

后台定时器、向量检索、模型工具调用、多模态、加密和 Web 界面均为可选能力，不得作为 Core 的必要条件。

## 4．平台无关数据模型

### 4.1 交换文档

Core 的规范交换根对象为 `AuSMExchange/0.1`，完整 JSON Schema 见配套文件。其组成如下：

| 对象 | 必需语义 |
| --- | --- |
| `history` | 有序自传历史记录，包含叙述、作用域、记录时间和证据引用 |
| `snapshots` | 快照修订序列，包含当前正文、修订号、生成主体及历史依据 |
| `anchors` | 可回源的长期具体信息及其有效或作废状态 |
| `confirmations` | 用户或授权主体对反思的待确认、确认、否决或悬置状态 |
| `extensions` | 命名空间化的宿主扩展，不得改写核心字段含义 |

`snapshots` 的最后一个有效修订是当前快照；实现可以只持久化当前快照和有限历史，但导出时必须如实标明实际保留范围。

### 4.2 标识、时间与扩展

- `history`、`snapshots`、`anchors`、`confirmations` 的 ID 分别在所属集合内唯一；`evidence.id` 在所属历史记录内唯一。跨系统引用应使用宿主命名空间或稳定 URI，不得仅凭数组位置推断身份。
- Core 交换时间使用带时区偏移的 RFC 3339 `date-time`。由本地朴素时间转换时必须明确时区；无法确定精确时间时使用扩展字段表达不确定性，不得伪造 UTC。
- `scope.kind` 允许 `private`、`group` 和 `custom`；自定义作用域规则由 Profile 定义，Core 不猜测其授权语义。
- `extensions` 的键应采用拥有者控制的反向域名或明确命名空间。接收方无法解释扩展时可以忽略其展示，但不得把扩展内容提升为核心事实。
- 核心字段中的空数组、空字符串与 `null` 不得随意互换；各字段规则以 Schema 为准。

### 4.3 引用完整性

1. 文档内证据引用采用 `<history_id>#<evidence_id>`，指向某一历史记录内的证据；`evidence.ref` 可以另存宿主内部定位符或外部 URI，但不能替代核心引用。
2. `snapshots[].based_on` 只能引用已存在的 `history[].id`。
3. `snapshots[].anchor_refs` 和 `confirmation_refs` 只能引用相应集合中已存在的对象 ID。
4. `anchors[].evidence_refs` 与 `confirmations[].evidence_refs` 必须能解析到至少一个历史记录中的证据；该证据可以标记为显式外部来源。无法解析的记录不得伪装成已回源。
5. `snapshots[].previous` 只能指向较早修订；首版为 `null`，不得形成循环。
6. `superseded` 锚点必须有非空 `supersession`；`active` 锚点的 `supersession` 必须为 `null`。`confirmed` 确认事项必须有非空确认主体和时间，其他状态不得伪造确认信息。

### 4.4 Core 不规定的物理细节

以下内容属于 Profile：文件目录、数据库表、压缩、签名公式、加密、分词器、检索算法、token 估算公式、模型提示词、后台调度、UI、容量数值与兼容旧版本方式。

Core 只要求这些选择不得破坏核心不变量，并且影响互操作或边界的部分必须公开。

## 5．生命周期

### 5.1 整合

```text
新事件 + 显式交代 + 可选外部素材
                ↓
       确定增量范围与作用域
                ↓
       写 / 不写 / 重试 / 降级
                ↓
      追加历史并保存来源与证据引用
                ↓
       生成新的快照修订或保留旧版
```

1. 实现必须能够识别已处理增量，或在游标失效时明确标记可能重叠。
2. 模型可以决定不写一般内容，但显式交代必须走独立保留通道。
3. 历史保存成功而快照失败时，历史可以保留，上一有效快照必须保留；不得声称二者处于全局事务中，除非 Profile 确实提供该保证。
4. 整合可以吸收旧简记或低层记录，但只能增加明确的吸收关系，不得删除旧正文。
5. 外部素材必须保留来源，不得未经标记伪装成 Agent 亲身经历。

### 5.2 快照更新

- 快照可以采用滚段、整篇重写或 Profile 定义的其他方式。
- 每次更新必须产生递增修订；历史正文不随快照回写。
- 快照可以遗漏细节，必须保留历史回源通道。
- 新快照应记录生成模型或等价生产者信息；模型替换后不得抹掉旧快照的来源。
- 事实级反思需要确认时，只有获得授权主体确认后才能进入有效确认事项。

### 5.3 语义冲突

| 冲突 | Core 处理规则 |
| --- | --- |
| 历史状态与当前状态不同 | 历史保留为过去状态，快照表达当前状态 |
| 用户纠正旧认识 | 保存纠正原话，更新当前理解，不覆盖旧历史 |
| 锚点失效 | 追加作废状态与原因，默认工作集排除 |
| 外部来源互相矛盾 | 保留来源与证据，不以排名代替真值判断 |
| 新旧快照同时存在 | 以有效最新修订为当前视图，旧版按公开策略保留 |

Core 不提供自然语言真值求解器；无法自动消解的冲突必须允许保持不确定或请求用户裁决。

### 5.4 交接

交接工作集按以下优先级由 Profile 具体预算化：

1. 当前快照；
2. 当前有效确认事项与锚点；
3. 近期历史或轻量节选；
4. 当前查询命中的旧证据；
5. 用户明确请求的全文。

工作集必须遵守作用域与预算。默认不自动遍历全部历史，不把历史总量直接转化为每轮 token 成本。手工交接也必须明确实际交付范围，不得把“数据存在”说成“模型已读”。

### 5.5 检索与派生索引

AuSM 不排斥 RAG、FTS、向量检索或重排。Core 规定它们在路线中的位置：**检索负责按需回源，快照负责当前理解，二者不得互相冒充。**

检索结果只能来自权威历史或显式外部来源；模型可以改写查询、排序候选，但不得生成不存在的证据。索引删除后必须能够从权威数据重建或退化到无索引读取。

### 5.6 导出、导入与删除

- 导出清单必须列明包含与排除的对象，不得用“全部数据”含糊带过。
- 导入必须先验证，再安放；已有数据冲突时不得静默覆盖。
- 迁移语义无损只覆盖实际导出的核心对象与引用关系，不覆盖未导出的运行状态。
- 用户明确删除是合法主权行为；删除传播、墓碑和跨设备重放策略属于 Profile，必须公开。
- 密钥、凭证、密码、访问令牌默认不得进入普通交换文档；确需迁移时必须使用单独的安全通道。

## 6．一致性验收

### 6.1 声明等级

| 声明 | 通过条件 |
| --- | --- |
| **Core-Structural** | 交换文档通过 Schema 与引用完整性检查 |
| **Core-Lifecycle** | 通过 C-01 至 C-15 中适用的全部生命周期测试，并公开不适用理由 |
| **Core-Interchange** | 两个不同宿主 Profile 均能读写同一黄金语料，保持核心语义，并分别通过 Structural 与 Lifecycle |
| **平台无关实现** | 至少两个不同宿主完成 Core-Interchange；在此之前只能表述为“按平台无关目标设计” |

“两个宿主”不要求必须由不同作者实现。作者自己的第二适配器验证可移植性；第三方独立实现进一步验证规范可理解性，两者不得互相冒充。

### 6.2 最低测试集

| 编号 | 测试 | 通过条件 |
| --- | --- | --- |
| **C-01** | Schema 验证 | 合法文档通过，缺必填字段、错误枚举和错误类型失败 |
| **C-02** | 历史追加 | 整合前后旧历史正文保持一致 |
| **C-03** | 快照修订 | 新修订递增，旧修订按声明策略保留 |
| **C-04** | 快照失败 | 模型或存储失败不覆盖上一有效快照 |
| **C-05** | 显式交代 | 模型选择不写时，显式交代仍被保留 |
| **C-06** | 证据引用 | 快照、锚点与确认事项的引用可解析，无悬空引用 |
| **C-07** | 时间更新 | 旧状态保持历史意义，当前状态由新修订表达 |
| **C-08** | 锚点作废 | 作废记录保留，默认工作集不再使用 |
| **C-09** | 交接预算 | 超预算只减少工作集，权威存储不变 |
| **C-10** | 作用域隔离 | 私有与不同群组数据在检索、交接和导出中不串域 |
| **C-11** | 索引重建 | 删除索引后可以从权威数据重建或退化读取 |
| **C-12** | 迁移往返 | 包含对象规范化内容与引用关系一致 |
| **C-13** | 检索不造证 | 查询扩展和重排不产生权威历史之外的新证据 |
| **C-14** | 跨模型交接 | 新模型读取旧记录后仍保留旧生产者信息与来源边界 |
| **C-15** | 扩展往返 | 未解释扩展不被误读为核心事实，并按 Profile 声明保留或剔除 |

### 6.3 黄金语料

一致性实现应公开至少一组合成语料，覆盖：

- 普通跨会话计划；
- 用户明确交代与纠正；
- 已完成的旧计划和过期状态；
- 自相矛盾的外部来源；
- AI self-report 与用户事实的区分；
- 私有两个不同作用域及一个显式共享作用域；
- 上下文预算不足；
- 模型 A 写入、模型 B 接管；
- 无证据问题和应拒答问题；
- 导出、导入和重复导入。

黄金语料不得依赖真实用户隐私，也不得只包含 AuSM 容易回答的案例。

## 7．主张、边界与证据状态

### 7.1 Core 可以提供的契约

- 可区分的自传历史、当前快照、锚点和确认状态；
- 可验证的历史不变量、作用域、回源和迁移规则；
- 可导出的开放平台无关交换模型；
- 可通过多宿主一致性测试检验的可移植性目标；
- 可在相同模型与预算下接受对照实验的系统设计。

### 7.2 Core 不保证的事项

- 不保证原始对话到自传历史的信息无损；
- 不保证快照包含全部重要细节；
- 不保证内容真实、语义召回完备或模型输出可复现；
- 不保证自动消解所有自然语言冲突；
- 不保证无限规模、任意并发或跨设备多主同步；
- 不保证模型内部形成长期记忆；
- 不保证 Agent self-report 对应真实感受；
- 不保证 AuSM 在所有连续性任务上优于摘要、画像或 RAG；
- 不保证单一实现即可证明全平台通用。

### 7.3 当前证据状态

截至本草案日期：

- Memory Diary Profile 提供一个真实 AstrBot 参考实现；
- Core-Structural 已具备独立 Schema 草案；
- 跨宿主黄金语料与自动化 Core-Interchange 测试尚待完成；
- 第二宿主与第三方独立实现尚待完成；
- 与摘要、画像、RAG 等路线的同预算对照、消融、规模与长期盲评尚未形成公开论文证据。

因此，当前准确表述是：

> **AuSM 已具备平台无关的核心规范草案和一个参考实现，正在向多宿主互操作与同预算实证评估推进。**

不得提前写成“已经证明全平台通用”或“已经证明优于现有记忆系统”。
